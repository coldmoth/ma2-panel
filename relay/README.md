# Сервер диагностики

Отдельный FastAPI-сервис принимает `PUT /v1/reports/{canonical UUID}` с JSON
`{"report": {...}}`. Квитанция содержит только `report_id`, `state`
(`queued`, `pending`, `sent`) и `number` для `sent`.
`GET /v1/reports/{UUID}` возвращает такую же квитанцию, неизвестный UUID — 404.
Тело и описание публично прочитать нельзя. `GET /health` возвращает `ok` и
`delivery_ready`: последнее означает наличие корректного файла credentials,
а не проверенную доступность GitHub или успешную сквозную отправку.

Приём подтверждается после SQLite commit с `synchronous=FULL`. Одинаковый UUID
с тем же нормализованным JSON возвращает квитанцию; иное содержимое — 409.
Отчёты и отдельные журналы Uploader сохраняются в каталоге состояния.
Принятые отчёты автоматически не удаляются. Резервировать/копировать нужно весь
каталог состояния, включая SQLite и `journals`, согласованно с остановкой сервиса.
Удаление журнала может потерять неопределённый результат GitHub POST.

Лимиты по умолчанию:

- 64 KiB UTF-8 на HTTP body и строгая схема `build_report` / `collect_report`;
  описание до 1000 символов, `captured_at` — ISO timestamp с часовым поясом.
- 5000 сохранённых отчётов всего; достижение ёмкости даёт 503.
- Новые отчёты: 20/мин всего, 5/час на IP; превышение даёт 429.
- Все HTTP-запросы, включая идемпотентные повторы и health: 120/мин всего.
- Попытки GitHub create: 30/час всего; резерв сохраняется до POST и при ошибке
  не возвращается. При исчерпании отчёт остаётся в очереди.
- Все фактические GitHub API-запросы, включая страницы поиска: 1000/час.
  После исчерпания квоты время следующей попытки сохраняется в SQLite;
  отложенные новые отчёты не перечитывают GitHub каждую минуту. Проверки pending
  допускаются при исчерпанной create-квоте, пока остаётся общий API-бюджет.
  Worker берёт до 20 отчётов за проход в порядке давности последней попытки.

Квоты хранятся в SQLite. История запросов очищается за пределами минуты,
приёма и создания — часа; произвольные IP не создают неограниченного кэша.
Идемпотентные повторы обходят только квоты новых отчётов и лимит ёмкости.
Ошибки диска возвращают 503. Payload и токен не записываются в логи.
Дисковая ёмкость ограничена количеством и размером отчётов, но файловая система
должна иметь запас для SQLite и копий в журналах (не менее 1 GiB).

Worker последовательно обходит независимые журналы всех неотправленных UUID
раз в минуту. Перед первым POST ищет UUID marker в закрытом репозитории,
сохраняя миграцию без дубля. Неоднозначный POST сохраняет `pending`: далее
разрешён только поиск, без повторного создания. Pending одного UUID не блокирует
остальные. После рестарта состояние `sent` восстанавливается из журнала, если
GitHub уже ответил, а SQLite-квитанция ещё не была обновлена. Ошибки отдельного
отчёта не останавливают worker. У сервиса должен быть ровно один процесс/worker.

## Однократная установка владельцем сервера

Код разместить в `/opt/ma2-diagnostics` с готовым `.venv` проекта; новых Python
зависимостей нет. Создать системного пользователя/группу `ma2-diagnostics` без
интерактивного shell. Код принадлежит root и недоступен сервису для записи.
Установить unit из `relay/ma2-diagnostics.service` в `/etc/systemd/system/`.
Systemd создаёт `/var/lib/ma2-diagnostics` с правами 0700.

Ограниченный GitHub-токен только для `coldmoth/ma2-panel-diagnostics` с Issues
read/write и Metadata read установить безопасным способом в
`/etc/ma2-diagnostics/github.json`:

```json
{"repository": "coldmoth/ma2-panel-diagnostics", "token": "<server-only token>"}
```

Каталог: root:ma2-diagnostics, 0750. Файл: root:ma2-diagnostics, 0640.
Для однократного безопасного ввода и установки использовать
`uv run python scripts/setup_diagnostic_relay.py` из корня проекта на Mac владельца.
Не копировать широкий CLI-токен и не добавлять токен в unit, аргументы процесса,
Git, отчёты, логи или чат. Токен читает только существующий Uploader.
Без файла сервис сохраняет очередь, а health показывает `delivery_ready: false`.

За существующим Caddy добавить отдельный hostname, не менять другие сайты:

```caddy
 diag.shmyrev52.ru {
     request_body {
         max_size 64KB
     }
     reverse_proxy 127.0.0.1:8767
 }
```

Проверить конфигурацию Caddy перед reload. Uvicorn доверяет proxy headers только
от `127.0.0.1`; Caddy должен оставаться единственным публичным входом и корректно
перезаписывать `X-Forwarded-For`. Не открывать порт 8767 наружу. Размер ограничен
также приложением, включая запросы без Content-Length. Не включать access logs
с телами/заголовками авторизации. Верификацию HTTPS выполнять только
синтетическими отчётами; наличие очереди не означает создание GitHub Issue.

## Локальная проверка

```sh
uv run pytest -q -p no:cacheprovider tests/test_diagnostic_relay_server.py
```

Тесты используют TestClient/lifespan, временные каталоги и GitHub-заглушки;
пульт и GitHub не вызываются.

## PAT: получение, замена и проверка перед залом (2026-11-03)

На ПК зала токен **не нужен**. `.env` предназначен для локальных инструментов,
`secret.env` — для пароля MA2. Новая доставка через relay не читает PAT из этих
файлов. `diagnostic_setup.py` относится к прежней прямой отправке и не является
настройкой нового комплекта. Не заменять серверный токен широким токеном `gh`.

1. В GitHub владельца: Settings → Developer settings → Personal access tokens →
   Fine-grained tokens → Generate new token. Выбрать владельца `coldmoth`,
   Only select repositories → `ma2-panel-diagnostics`; Repository permissions:
   Issues — Read and write, Metadata — Read. Указать срок действия, записать дату
   продления в личном календаре. Создание и подтверждения GitHub выполняет владелец.
2. На Mac владельца запустить `uv run python scripts/setup_diagnostic_relay.py`.
   Вставить токен в скрытый интерактивный ввод; не передавать его аргументом,
   переменной в shell history, в чат или отчёт. Скрипт проверяет приватность репозитория,
   передаёт токен по stdin SSH и устанавливает `/etc/ma2-diagnostics/github.json`
   с правами из предыдущего раздела, затем перезапускает сервис. Нужны уже настроенные
   SSH-ключ, known_hosts и установленный сервер; скрипт их не создаёт.
3. `https://diag.shmyrev52.ru/health`: `delivery_ready: true` подтверждает чтение
   файла доступа, но не проверяет срок PAT и право создавать Issues. Проверка
   `Github(token).check_private()` на сервере подтверждает доступ к приватному
   репозиторию; только доставка тестового UUID с номером Issue проверяет запись.
4. Через localhost панели создать один явно помеченный тестовый mock-отчёт.
   Дождаться «отправлен» и номера Issue: «принят сервером» ещё не успех GitHub.
   При тайм-ауте сохранять UUID и проверять его квитанцию, не создавать новый отчёт.
   Сервер продолжит доставку даже после закрытия браузера. Не отправлять сырой diag.zip
   как тест PAT: автоматическая отправка специально не содержит исходных ответов.
5. При истечении/отзыве PAT повторить скрытую установку, сохранив SQLite и journals.
   Не удалять очередь и не повторять неоднозначный GitHub POST вручную.

Источник: [GitHub — управление PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens),
[права fine-grained PAT](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens).
Обновление схемы версий отчёта требует сначала обновить приёмник: старый сервер
принимает только прежний формат даты/коммита, новый также принимает `3.1.0rc1`
и ограниченный суффикс сборки (`+<hash>[-dirty]` или `+nogit`).

## Раздел readback (2026-11-08)

Сначала обновить приёмник: diagnostic_readback.py, diagnostic_upload.py и relay/app.py.
Раздел необязателен: прежние отчёты и их UUID сохраняются. Новый раздел строго
проверяется; исходные Lua, имена, пути и абсолютные адреса запрещены.
После проверки /health и локальной валидации старого/нового синтетических
снимков выпускать панель. Сохранённый старый отчёт не пересобирается: после
обновления для новых полей нужен новый снимок кнопкой отправки. Не удалять
SQLite/журналы/credentials при обновлении или откате сервера.
