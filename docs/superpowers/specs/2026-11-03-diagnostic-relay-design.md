# Диагностика без настройки доступа на пользовательском ПК

Статус: утверждён владельцем в чате 2026-11-03.

## Цель и границы

На новой установке пользователь нажимает «Отправить диагностику» без аккаунта
GitHub, токена и редактирования файлов. Получатель — закрытый репозиторий
`coldmoth/ma2-panel-diagnostics` через HTTPS-приёмник `diag.shmyrev52.ru`.
Владелец предоставил сервер и создал DNS. Мастер первого подключения к MA2 —
следующий независимый патч; этот патч не отправляет команды MA2.

## Варианты

- Токен на каждом ПК: существующее решение, требует ручной настройки доступа.
- Токен внутри дистрибутива: раскрывает общий GitHub-доступ; не использовать.
- Общий HTTPS-приёмник: выбранная с владельцем схема; требует серверного сервиса,
  HTTPS и однократной настройки GitHub-доступа владельцем на сервере.

## Поведение

1. Согласие на передачу — существующая кнопка. Необязательное описание,
   обезличивание, UUID, неизменяемый снимок и очередь на ПК сохраняются.
2. По умолчанию мост доставляет отчёт только фиксированному HTTPS-приёмнику.
   Пользовательский ПК не хранит GitHub-токен. Перенаправления не принимаются.
3. Приёмник сначала надёжно сохраняет отчёт, затем фоновый обработчик создаёт
   Issue. Приём сервером и подтверждённая отправка в GitHub — разные состояния.
4. Повтор того же UUID и содержимого возвращает текущую квитанцию. Другое
   содержимое под тем же UUID отклоняется. Публичный запрос статуса не раскрывает
   описание и тело отчёта.
5. После потери ответа ПК безопасно повторяет идемпотентный запрос приёмнику.
   На границе приёмник → GitHub сохраняется поиск по UUID и запрет повторного
   POST при неоднозначном результате. Проверка закрытости репозитория сохраняется.
6. Отсутствие интернета, рестарт браузера/моста/приёмника не теряют уже сохранённый
   отчёт. Ошибка GitHub не выдаётся за успешную доставку. После подтверждения
   показываются номер Issue и возможность отправить новый отчёт.
7. Ранее сохранённые отчёты не получают нового согласия автоматически.
   Миграция существующих незавершённых отправок должна исключать дубли Issue;
   старые настройки доступа не удаляются и секреты не попадают в отчёты.

## Сервер и ограничения

Отдельный непривилегированный systemd-сервис за существующим Caddy; приложение
слушает только loopback. Очередь сохраняется на диске. Код и данные отделены,
существующие сайты и контейнеры не меняются. Ограниченный GitHub-токен хранится
только на сервере с закрытыми правами; широкий локальный CLI-токен не копируется.

Публичный приёмник принимает только ограниченный формат и размер, ограничивает
частоту запросов, общую очередь и выдачу в GitHub. Общий секрет внутри клиента
не считается защитой от спама. Нужны ограничение расхода диска и понятный отказ
при перегрузке. Сохраняются существующие правила отсутствия автоматического
удаления принятых отчётов до отдельного решения владельца.

## Проверки и контракт

До изменения реализации: регрессионные тесты и нужное падение. Проверить приём
без credentials на ПК, повторы/конфликт UUID, потерянный ответ, рестарты, offline,
ограничения формата/нагрузки, отказ и неоднозначность GitHub, приватность статуса,
миграцию очереди. Затем полный pytest, Node, визуальная проверка в изолированном
mock, независимый review и синтетическая доставка через живой HTTPS-приёмник.
Рабочие данные площадки и настоящий пульт не использовать.

После согласия владельца обновить раздел «Диагностика» в `docs/spec.md` и
датированную историю: заменить требование GitHub-токена на ПК фиксированным
приёмником, описать серверную квитанцию, две очереди и однократный серверный доступ.
Самопроверку, состав релиза и документацию согласовать с новой схемой.

## Открытое условие запуска

Для доставки в GitHub потребуется однократно установить на сервер ограниченный
токен с доступом только к репозиторию диагностики (Issues read/write, Metadata read).
Без этого сервер может хранить очередь, но считать сквозную отправку готовой нельзя.
